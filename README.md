# Claude Code 繁體中文回話風格（Output Style）

用 Claude Code 的 output style 功能，把「AI 助理該怎麼跟你說話」寫成一個檔案。這個 repo 是我們實際在用的版本，含完整的痛點、設計想法與安裝步驟。

規則本體是 [`output-styles/zhtw-style.md`](output-styles/zhtw-style.md)，另外三支 hook 負責讓規則真的被執行：

| 檔案 | 掛在哪 | 做什麼 |
|---|---|---|
| [`hooks/zhtw_turn_reminder.py`](hooks/zhtw_turn_reminder.py) | UserPromptSubmit | 每一輪開頭注入一行語言提醒 |
| [`hooks/zhtw_live_gate.py`](hooks/zhtw_live_gate.py) | PreToolUse | 檢查剛講的進度短句，違規就擋下一個工具 |
| [`hooks/zhtw_gate.py`](hooks/zhtw_gate.py) | Stop | 收尾前掃這一輪講過的每一句 |

三支都是選用的，只裝規則本體也能用。

## 痛點：為什麼要管 AI 的說話方式

這些都是長期使用累積出來的真實痛點，不是想像出來的：

1. **簡體字混入**。你用繁體問，它用繁體答——直到它查了一篇簡體資料，接下來整段回答就跟著變簡體。對只讀繁體的使用者，這等於看不懂。
2. **中英夾雜**。「這個 approach 的 tradeoff 是……」讀起來很累。術語可以留英文，敘述不行。
3. **簡單問題長篇大論**。問一句「這是什麼」，回來一張 18 列的比較表加五個小節。
4. **術語轟炸**。丟出 α、t 值、σ 卻不翻譯成白話，也不套回你自己的數字。
5. **報喜不報憂**。說「做完了」但沒證據；查詢逾時被寫成「查無資料」；跳過的步驟不講。
6. **規則寫了不執行**。以上每一條都寫過規則，但規則放在筆記裡，模型想不起來就等於不存在。

## 原因：這些毛病從哪來

- **訓練資料分布**：中文語料以簡體為大宗，模型的中文「預設腔」偏簡體與大陸用語。
- **語言漂移的入口在讀取，不在輸出**：模型傾向跟隨 context 裡最近出現的語言。讀了簡體資料，輸出就被帶走。所以只叮嚀「輸出前自查」治標，要從入口鎖定。
- **有用性偏好**：模型被訓練成「多給一點比較保險」，於是簡單問題也給出完整報告。
- **規則的送達方式**：放在記憶或筆記裡的規則是「機率性存在」——被檢索到才有效。output style 每個 session 保證注入，這是它跟筆記最大的差別。

## 想法：設計上的幾個決定

**風格層與業務規則分層。** output style 只管「怎麼說話」，專案的業務規則（該做什麼、怎麼派工）留在 CLAUDE.md。兩層各自演化，互不重複。

**語言鎖定管入口。** 規則寫成「回覆語言只由使用者當次訊息決定，整輪不變；禁止從讀進來的資料推斷語言」。這是治根因的那一條——簡體混入幾乎都來自「查了簡體材料就跟著用」。

**借 STE100 的原則層。** ASD-STE100 是航太業的受控語言規範（Simplified Technical English），核心是一詞一義、一句一事、句短、主動語態。原版管的是英文詞彙表與文法，詞彙表搬不動，但原則可以在地化成中文寫作規則。技術溝通的可讀性問題，航太業五十年前就解過一輪。

**收據文化：用輸出格式逼出執行。** 「要誠實」這種原則性規則會被靜默跳過，因為沒有任何東西檢查輸出裡有沒有它。改成硬性格式——派過工就必須附一行 `[派工收據]`，查過資料庫就必須附進度表——沒附就等於沒做完。規則要進輸出格式，否則是裝飾。

**留一個違規訊號。** 使用者說「我看不懂」「太多術語」，定義為當場違規，立刻重講白話版。這給了風格一個可執行的回饋迴圈，而不是抽象的期許。

## 第二版：為什麼第一版沒有用

第一版上線當天，使用者的第一個反應是：**「我覺得你 output 的沒有變，設定這個真的有差嗎？」**

我們去查了機制，機制是好的：`settings.json` 確實設了風格、檔案確實整份注入了 system prompt。
問題不在機制，在內容——**第一版有九成是把既有的 CLAUDE.md 鐵律再抄一次**。

**九成重疊的設定，帶不出九成的改變。**

第一版真正新增的只有 STE100 那一節，而寫規則的人當天就違反了它，寫出這種句子：

> 原因：那是公司的工作內容，依資安紅線不進資料庫，所以找不到合格的來源連結（閘門要求來源必須是某兩個目錄底下的既有 .md）。

一句 60 幾個字，講了三件事。照自己訂的規則該拆成三句。

於是第二版整份重寫，換一個設定方式：**不寫「請簡潔」，改寫「對方是九歲小孩」。**

差別在哪：

- 「請簡潔」是**程度**的要求。模型可以自認已經很簡潔了。
- 「對方是九歲小孩」是**對象**的設定。九歲小孩聽不懂「stale」「rate limit」「kill switch」，這是事實判斷，沒有模糊空間。

第二版還加了一條收尾：**「他聽不懂，就是你講錯了，不是他笨。」** 把舉證責任放在寫的人身上。

### 從這件事學到的三條

1. **風格層只放 CLAUDE.md 沒有的東西。** 把業務規則抄進風格層，看起來很完整，實際上什麼都沒改變。
2. **設定對象比設定程度有效。** 「簡潔」「白話」「淺顯」都可以自我感覺良好，「九歲小孩看得懂」不行。
3. **先查機制再改內容。** 使用者說「沒效」的時候，第一步是確認設定真的生效了——如果直接開始改內容，你可能在修一個沒壞的東西。

## 第三版：規則擋不住，要有東西攔

第二版上線之後，說話方式確實變了。但一個月內同一件事又發生兩次：使用者回報「你又開始說英文了」。

規則沒有變模糊，也沒有被刪掉。它就寫在第二條，白紙黑字。

**問題是：沒有任何東西會在送出前看一眼。**

這跟第一版的失敗不同。第一版是內容不對，第三版要處理的是**內容對了但沒被執行**。原則性的規則會被靜默跳過，因為跳過它不會有任何後果——沒有紅字、沒有攔截，下一秒就送出去了。

於是加一支 stop hook：回話送出前掃一遍，違規就擋下來，把違規的那一行印出來，改完才准收尾。

### 掛錯位置的檢查等於沒有檢查

第一版的 hook 只看 `last_assistant_message`，也就是整輪的最後一則訊息。

上線後又被抓到說英文，而且是同一個人、同一種違規。去查才發現：那些英文全出現在**做事中間的進度短句**上——「Now the feed side」「All three kinds route correctly」這種一行字。工具跑完接一句、再跑一個工具接一句，這些都不是最後一則，hook 一個字都沒看到。

修法是讓 hook 讀逐字檔，往回收到最後一則使用者訊息為止，把這一輪講過的每一句都納入檢查。

同一天風格檔也補了一行，因為原本寫「整篇繁體中文」，而中途的短句不覺得自己是「一篇」：

> 這條管每一則訊息，不是只管最後那則。做事中間插的一句進度短句也算。

**教訓：檢查站要放在出事的地方。** 規則對、檢查也寫了，但檢查看不到違規發生的位置，結果跟沒有檢查一樣。

### 這道閘做不到什麼（裝之前先知道）

它是收尾時才跑的檢查。**中途的訊息在螢幕上出現的當下，它攔不下來。**

也就是說：你還是會看到那句英文。閘能做的是在那一輪要結束時把模型擋住，逼它回頭改，而不是讓那句話一開始就不出現。

Claude Code 目前沒有提供「送出中途訊息之前」的攔截點，所以這件事沒有純機械解。這道閘的價值在於**違規不能就這樣過去**——有紅字、有記錄、要改完才收得了工。真正的預防還是在規則本身，閘只是最後一道網。

寫這段的當天，模型正在改這個 repo 的過程中又講了一次英文，而閘沒有攔住那一句。這個限制是實測出來的，不是推測。

### 判定條件（刻意保守）

寧可漏抓，不要誤擋。誤擋一次就會被關掉，關掉之後就什麼都不剩。

1. **整句英文**：一行裡連續六個以上的英文單字才算。判斷前先把反引號裡的程式碼、網址、檔案路徑、引號裡的引文挖掉——識別碼、指令、引用原文本來就該留原樣。
2. **簡體字**：命中常見簡體字表。同樣先挖掉引號內的內容，因為引簡體原文再加註是合法的。
3. 程式碼區塊（三個反引號之間）與縮排的程式碼整段不掃。

退出碼 0 放行，2 擋下並把原因印到標準錯誤。`stop_hook_active` 為真時直接放行，避免無限迴圈。讀不到輸入或讀不到逐字檔時一律放行——檢查自己壞掉不該擋住你工作。

## 第四版：找到真正的犯案位置

第三版上線的那一天，同一個人又抓到兩次說英文。其中一次是在**修這個毛病的同一輪裡**再犯。

前三版都在問「規則寫得夠不夠清楚」。第四版改問一個不一樣的問題：**那些英文句子到底出現在哪裡？**

去翻當天的逐字檔，把所有英文句子撈出來看，答案很清楚：**全部都是工具與工具之間的那一句進度短句。**沒有一句出現在最後交出去的回答裡。

為什麼是那一句：

1. **它緊接在英文之後。** 上一秒才讀完滿螢幕的命令輸出、程式碼、錯誤訊息，下一句話就跟著英文走。語言漂移的入口在讀取，這在前面第二節就寫過了，但沒有人想到它會挑這個位置下手。
2. **寫它的時候幾乎不思考。** 最後那則回答是慢慢寫的，會想到風格；中間那一句是順手帶過的，預設語言就贏了。
3. **它不覺得自己是「一篇」。** 規則寫「整篇繁體中文」，一句十個字的進度短句不會把自己當成一篇。

三個特性湊在一起，就是這個毛病一直治不好的原因。

### 一個實驗改變了做法

原本以為沒救，因為那句話顯示出來的當下沒有攔截點。後來去看逐字檔的結構，發現一件事：

**進度短句與工具呼叫是兩列，而且文字那列先寫進逐字檔。**

這代表 `PreToolUse` 這個時機**看得到剛講完的那句話**。攔不住它被顯示，但攔得住下一個動作。

於是有了 [`hooks/zhtw_live_gate.py`](hooks/zhtw_live_gate.py)：一講英文，下一個工具就被擋下來，錯誤訊息直接回到模型面前，逼它當場用中文重講。

### 一個必踩的坑：同一句只能擋一次

違規的句子會留在逐字檔裡。如果每次都擋，下一個工具永遠過不去，整輪死鎖。

所以擋過的句子要記下來（存 sha1 到一個 state 檔），同一句只擋一次。警告送到就放行，讓工作繼續。

### 驗證方式：拿真實紀錄回放

不要用自己編的例子測，用當天的逐字檔回放：

| 測什麼 | 結果 |
|---|---|
| 當天實際講出來的英文短句 | 22 句，全部攔下 |
| 當天含中文的訊息 | 162 則，只有 1 則被擋 |
| 那 1 則是不是誤擋 | 不是，它真的夾了英文 |

攔截率 100%，誤擋 0。這個數字是回放真實資料得到的，不是設計時的期望值。

### 三層各自負責什麼

- **每輪提醒**（UserPromptSubmit）：風格檔是 session 開頭注入一次，一輪跑上百個工具之後離得太遠。這一層把提醒放到離違規最近的地方。
- **當場擋**（PreToolUse）：唯一能在一輪之中產生後果的一層。
- **收尾檢查**（Stop）：最後一道網，掃這一輪講過的每一句。

三層都攔不住那句話被顯示出來。能做到的是：**違規不能就這樣過去。**

## 實際操作：安裝三步

1. 建目錄（已存在就跳過）：

   ```bash
   mkdir -p ~/.claude/output-styles
   ```

2. 把 [`output-styles/zhtw-style.md`](output-styles/zhtw-style.md) 複製進去：

   ```bash
   cp output-styles/zhtw-style.md ~/.claude/output-styles/
   ```

3. 在 Claude Code 裡執行 `/config`，找到「輸出風格（Output style）」，選「繁中簡明風格」。

改了檔案內容之後，重選一次風格或開新 session 才會生效。

### 第四步（選用）：掛上三層 hook

規則會被跳過，所以建議連檢查一起裝。三支複製進去：

```bash
mkdir -p ~/.claude/hooks
cp hooks/zhtw_turn_reminder.py hooks/zhtw_live_gate.py hooks/zhtw_gate.py ~/.claude/hooks/
```

再編輯 `~/.claude/settings.json`，加這三個事件：

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python \"$HOME/.claude/hooks/zhtw_turn_reminder.py\""
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "python \"$HOME/.claude/hooks/zhtw_live_gate.py\""
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python \"$HOME/.claude/hooks/zhtw_gate.py\""
          }
        ]
      }
    ]
  }
}
```

已經有其他 hook 的話，把這幾支併進既有的陣列，不要整段覆蓋。

Windows 使用者把路徑換成絕對路徑，例如 `python "C:/Users/你的帳號/.claude/hooks/zhtw_live_gate.py"`。

裝好之後開新 session 才生效。想確認它活著，就叫 Claude 用英文講一句再做事，下一個動作應該會被擋下來。

`hooks/.zhtw_live_state.json` 是當場擋那支自己產生的紀錄檔，記「哪些句子已經警告過」。
把它加進 `.gitignore`，不需要版控。

## 檔案格式說明

output style 是一個帶 YAML frontmatter 的 markdown 檔：

```markdown
---
name: 顯示在選單上的名稱
description: 一句話說明
---

（以下整段會注入 system prompt，取代預設的回話風格指示）
```

`name` 是 `/config` 選單上看到的名稱。內文就是給模型的指示，寫法沒有限制——我們的經驗是：規則要可檢查（「句短」附上字數目標）、例外要明列（哪些東西保持原文）、違規要有訊號（什麼話等於踩線）。

## 改成你自己的版本

`zhtw-style.md` 裡有幾條是我們的環境特化，改掉就能通用：

- 第七條「做完要附證據」是我們的派工場景，單人使用可以整節刪掉，或換成你自己的檢查格式。
- 「九歲」這個年齡可以調。對象設定要具體到能做事實判斷，不要換回「請簡潔」這種程度形容詞。
- 風格名稱由 frontmatter 的 `name` 欄位決定，隨你改。
- 檢查閘的英文門檻是「連續六個英文單字」。你的工作如果本來就常出現長英文專有名詞，把 `EN_RUN` 的 `{6,}` 調大；寧可漏抓也不要誤擋。
